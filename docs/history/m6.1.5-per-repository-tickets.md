# M6.1.5 — Per-repository tickets

A ticket whose scope is given repository by repository: the lease's terms, then each
repository's, each part fitting a template that allows that repository, still one ticket,
one approval, one lease ([the lease model](../lease-model.md),
[the ticket file](../operators/ticket.md), [the design page](m6.1.5-per-repository-tickets-design.md)).
Added after M6.1 at the user's request; the design settled with the user (the decision log's
2026-11-04 M6.1.5 rows).

**Status:** done (2026-11-05), except the manual check with a real agent (the last
acceptance item but one, below), which needs a person. `make ci` passes; `make e2e` passes
(28 scenarios); the integration suite passes (132 run, 3 skipped). All run on macOS.

## What was planned

The roadmap's section, as it stood: the layout
(`common`, `repos.<repo>` with its template, operations, branches, force push, expected paths
and counts, the lease's `ticket` and `limits`), no override, the old layout refused naming
each key's new place, `writ-ticket/3` and a new state version; counts per repository only;
the lease-wide terms the strictest of its templates; one signing key per lease; narrowing per
repository; `writ policy` for several repositories; both skills rewritten; docs and
registries.

## What was done

- **The ticket** (`writ-core::ticket`): `Ticket { common, repos, text, limits, on_violation }`,
  `RepoTerms` per repository; the request the same, `common` optional, `repos` required;
  every old key refused naming its new place (`ticket::old_layout`). `writ-ticket/3`.
- **Fit** (`writ-core::fit`): each repository against its template, named, kept by a
  renewal, or the only one that allows it and fits (several: rejected naming the repository
  and the templates; a named template's own reasons said directly); one signing key and one
  committer name across the templates of the repositories that sign; the TTL, the rate and
  `max_renewals` within the strictest; the committer emails within every signing
  repository's template, and within the lease's templates even when no repository signs (a
  property test found that gap); at most 16 repositories, branches and paths bounded per
  repository, the paths' bytes in all. Omitted values: the intersection of the signing
  templates' emails, the smallest TTL and rate.
- **Policy and state**: every sign, push and fetch decided against its repository's part;
  signatures and pushes counted per repository (`writ-store`'s `usage` table, state version
  9); a repository used up refuses with `limit`, the lease used up when every repository is.
- **`writ sign`**: the lease's terms once, then a block per repository, within 78 columns;
  narrowing flags `[REPO:]VALUE` (a scoped count refused above that repository's, an unscoped
  one a cap; an unscoped `--branch` reaching the repositories that have branches).
- **Clients**: `writ policy <repo>…` with each template's signing key id and a "Together:"
  section that follows the fit (per key, where one lease could sign); the dry run and the
  grant line naming each repository's template; both skills in the new layout, their
  examples checked by `writ check` in a test.
- **Tests**: every ticket in every crate's tests rewritten (a temporary converter,
  `tool/m615_convert.py`, did the mechanical field uses; removed with this page); new
  `writ-core/tests/per_repository.rs`, `counters_are_per_repository` (store),
  `a_repository_used_up_leaves_the_others_their_signatures` (approval), the narrowing unit
  tests, and end-to-end scenario 22, `per_repository`.
- **Docs**: the lease model, approvals, clients, policy and state, gateway, flows, the
  operators' ticket and policy pages, the security inventory's ticket row, the threat model's
  count guarantee (counts per repository, no lease-wide cap), the registries.

## Decisions

In the [decision log](../decisions.md): the 2026-11-04 design rows, and the 2026-11-05 row

## The security checklist, for M6.1.5

1. **Inputs:** the ticket file's new shape: bounded (16 repositories, 50 branches and 100
   paths per repository, 16 KiB of paths in all), the old layout and misplaced keys refused,
   hostile `[REPO:]VALUE` flags refused; in the inventory.
2. **Authority:** none added; each repository's part within its own template, the lease-wide
   terms within the strictest, one key per lease. No lease-wide count cap, by design: the sum
   of the parts, which the approver sees and signs.
3. **Fail closed:** an ambiguous template, a missing one, different keys or names, an old
   layout or an older state: refused with the reason.
4. **Audit:** unchanged lines; the counts' denials name the repository.
5. **Revocation:** unchanged.
6. **Secrets:** `writ policy` shows a signing key's id, never key material (tested).
7. **Display:** the approver's screen per repository, every agent field cleaned, within 78
   columns (tested at the widest); the agent's lines name each template, cleaned.
8. **Dependencies:** none added.
9. **Guarantees:** the time, count and rate guarantee restated per repository, with its
   tests; nothing weakened beyond what was decided.
10. **Threat model:** updated (the count row, and the `writ policy` row's key id).

## Acceptance

- [x] One ticket for two repositories under two templates is granted with one signature, and
      each repository's requests are held to its own part.
      *`two_repositories_under_two_templates_are_one_lease_each_held_to_its_part`
      (writ-core: an operation, a branch and a path denied with their codes in one
      repository and allowed in the other); scenario 22 (`make e2e`, Forgejo): a path
      refused at signing (`paths`), pr-api's branch refused in pr-web (`ref`), pr-web's
      count (`limit`) while pr-api still pushes, one `grant` line.*
- [x] A repository whose terms fit no template rejects the whole ticket, naming it; so do
      repositories whose templates name different keys.
      *`a_repository_is_held_to_a_template_that_allows_it`,
      `templates_that_sign_with_different_keys_cannot_share_a_lease` (writ-core); the keys
      rejection end to end in scenario 22, each template and key named.*
- [x] Each part's counts hold on both sides; the TTL, rate and renewals the strictest.
      *`each_repository_s_counts_hold_on_both_sides`,
      `the_lease_s_time_and_rate_are_the_strictest_template_s_on_both_sides`,
      `the_lease_s_renewals_are_the_strictest_template_s_on_both_sides`,
      `counters_are_per_repository` (store). `on_violation` has nothing to combine: templates
