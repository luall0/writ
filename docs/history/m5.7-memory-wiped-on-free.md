# M5.7 — Memory wiped on free

Asked for by the user after M5.6's review. Writ wipes every copy of a secret it owns
(`Zeroizing`, buffers sized up front), but libraries keep their own and free them unwiped:
age's encryption buffer holds the plaintext of a key sealed at runtime, bech32's and age's
parse hold the keystore identity's encoding at unseal. A global allocator that zeroes every
block before handing it back to the system closes that for every library at once, in each
binary that handles a secret: `writd`, `writ` and `writ-sign`.

**Status:** done (2026-11-04). The allocator is Writ's own (`writ-alloc`), set in the three
binaries, on in every build: decided with the user from the benchmark below (Q39 closed).

## What was done

- **The allocator** (`crates/writ-alloc`, no dependency): `Wiping` wraps the system
  allocator. `alloc` and `alloc_zeroed` are the system's. `dealloc` zeroes the block's whole
  requested size (all that Rust code may have written), then frees it. `realloc` is the
  trait's default: a new block, a copy, the old block wiped and freed, never the system's
  own `realloc`, which may move a block and free the old one unwiped. Its `unsafe` code is in
  one module (`wipe`), each block with its `SAFETY` comment (hard rule 11); the test support
  is in another (`testing`, behind the `testing` feature).
- **Our own, not `zeroizing-alloc`** (asked by the user): the same idea is about 40 lines;
  1Password's crate is an example without tests. Ours zeroes with `memset` followed by an
  empty `asm!` block taking the block's pointer: without `nomem`, the compiler must assume the
  assembly reads the block, so the zeroes can't be removed as stores to memory about to be
  freed. glibc's `explicit_bzero` and Linux's `memzero_explicit` do the same.
- **The barrier is needed, and checked:** without it, `rustc -O` removes the zeroing
  entirely (`__rust_dealloc` is a single jump to `free`; seen on macOS arm64, release
  `writ-sign`). With it, `__rust_dealloc` calls `bzero` then `free`, and `__rust_realloc`
  `malloc`, `memcpy`, `bzero`, `free`. `tests/barrier.rs` compiles a program on the
  allocator with `rustc -O` and reads its `__rust_dealloc` both ways.
- **Set in the three binaries** as `#[global_allocator] static ALLOCATOR:
  writ_alloc::Wiping = writ_alloc::Wiping::system();`, checked by `tool/check-rules.py`, and
  by a test in each binary (`the_global_allocator_wipes_every_block_freed`: the count of
  blocks wiped, kept only in test builds, moves when a block is freed). `writd`'s
  `system-allocator` feature is the benchmark's baseline only, refused in a shipped build by
  `tool/check-features.py`.
- **The benchmark** (`make bench-alloc`, `tool/bench-alloc.py`,
  `crates/writ-integration/tests/alloc_bench.rs`): below.
- **Docs**: the threat model (a guarantee with its tests; the library-copies row narrowed to
  what stays: a live copy, the stack, other processes; the unseal and reader-key rows),
  [security.md](../security.md) (secrets, the `unsafe` modules, the checks),
  [conventions.md](../conventions.md) (the allocator in every binary that handles a
  secret), [stack.md](../stack.md), the [overview](../architecture/overview.md), the decision
  log (two rows; Q39 closed), AGENTS.md (`make bench-alloc`).

## The benchmark

The same work against two release builds of `writd`, one with the wiping allocator and one
with the system allocator alone (`--features writd/system-allocator`); `writ` and
`writ-sign` are the same (wiping) in both. Five runs per build, the builds alternated (each
goes first in turn).

- **The daemon under heavy load** (`writd_under_heavy_load`): the real `writd`, sealed then
  unsealed; 8 agents, each with its own home and lease, submitting their tickets at once,
  signed at once by the approver (half over SSH, half over HTTPS); then 12 rounds each of a
  fetch (every fetch syncs the one mirror they share from upstream), a signed commit of 3
  files and a push upstream on its own branch, all at once; meanwhile 8 more tickets
  submitted and signed in bursts and a signed policy change; then a 24 MiB push
  (incompressible) fetched by all 8 agents at once. Measured: each operation's latency, the
  wall time of each phase, `writd`'s own CPU time (`/proc` or `ps`), the CPU time of every
  process of the run (the daemon's hooks, relays and git, the agents' `writ`, git and ssh),
  `writd`'s resident memory sampled every 50 ms.
- **The allocation-heavy paths** (`allocation_heavy_paths`), in one process on
  `writ_alloc::testing::Switch` (the system allocator, wiping or not), each sample taken both
  ways, interleaved, 21 samples: a ticket parsed (YAML) and decoded (canonical), an audit
  line built and encoded, a commit's touched paths from its evidence (2,000 files), a buffer
  grown to 1 MiB a byte at a time, a 16 MiB buffer, 1,000 small strings.

To rerun: `make bench-alloc` on the Mac (`RUNS=<n>`, 5 by default), `make bench-alloc
LINUX=1` in a Linux container (the Rust image `e2e/Dockerfile` pins, glibc's allocator as in
detached mode). Every run's numbers land under `target/bench/results*/`.

### What the numbers say

- **Under heavy load, no measurable cost.** Throughput, latencies (p50 and p99) and memory
  moved within run-to-run noise on both systems (on macOS the noise even favored wiping:
  the storm's wall time varies by about 7 % between runs of one build). The daemon's work
  waits on git, ssh and the mirror lock, not on its allocator.
- **The CPU it adds is small:** `writd`'s own CPU time rose 5 % on Linux (0.13 s over a
  72 s run), every process's 1.4 %; nothing on macOS beyond noise.
- **The cost is real on the allocation-heavy paths alone:** glibc's small-block free is so
  cheap that zeroing shows (+37 % for 1,000 short strings, +15 % for a ticket decode), a large
  block costs its `memset` (+25 to +33 % for 16 MiB), and a growing buffer can never grow in
  place (+9 to +16 %). Each is microseconds per operation, against operations of tens of
  milliseconds to seconds.
- **Memory:** no change. On macOS the storm's peak (1 GiB in both builds, left out of the
  macOS table) is the unseal's key derivation (age's scrypt, about 1 GiB here), freed but
  kept resident by macOS's allocator for a while; the large phase shows the load's own.

## The security checklist, for M5.7

1. **Inputs:** not touched (no new input; the benchmark is test code).
2. **Authority:** not touched.
3. **Fail closed:** not touched. The allocator returns what the system's returns (a null on
   failure, which Rust turns into an abort, as before).
4. **Audit:** not touched.
5. **Revocation:** not touched.
6. **Secrets:** every block the three binaries free is zeroed first, whatever library made
   it; `realloc` never frees an old block unwiped; the zeroing is checked to survive the
   optimizer. What stays: a library's live copy, the stack and registers, other processes,
   the kernel's buffers (threat model).
7. **Display:** not touched.
8. **Dependencies:** none added (Writ's own crate, no dependency; `tempfile` for a test,
   already in the tree). `unsafe` in two dedicated modules of `writ-alloc`, each block with
   its `SAFETY`.
9. **Guarantees:** a new one, "every block freed is zeroed first", with its tests in the
   registry, each tried against a broken allocator (no zeroing: every test fails; `realloc`
   forwarded to the system's: the two `realloc` tests fail; no barrier: the barrier test
   fails).
10. **Threat model:** the library-copies, unseal and reader-key rows narrowed; nothing
    weakened.
