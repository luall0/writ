# M7.9.5 — Operator experience

Asked by the user after running the real install ([M7.9](m7.9-local-mode-checked-on-the-mac.md)):
what worked was still hard to use. Amendments now show only what they change; the approval
popup was redesigned on mockups the user validated, then built to them; every question
`writ` and the installer ask is a menu on a terminal; a quick start leads from `make install`
to an agent's first verified commit, and the operator pages stopped assuming one approval
agent. The forks settled with the user, at its start and while building it, are in the
[decision log](../decisions.md) (2026-11-15, M7.9.5).

**Status:** done (2026-11-15). `make ci` passes on macOS (1200 tests) and `make e2e`
passes (40 scenarios). The user tested the popup and the menus on their Mac, against a stand-in `writ` while
designing and on their own setup at the end; what they found was fixed here (below).

**Found while building it, and by the user's tests:**

- **Typed-ahead answers and widgets.** In raw mode Enter is `\r` and a typed `\n` is Ctrl-J,
  and a question asked by a process of its own reads every answer typed ahead and exits
  with them. The pipeline's and the integration tests' terminals now set `stty -icrnl`, type
  Enter as `\r`, and type each answer once the question before shows it answered; a command
  still asking a minute after its last answer is killed with its process group, so a missing
  answer fails readably instead of hanging (`ab7b307`, `abde3f2`).
- **A select can't take an answer it doesn't offer**: two tests typed one (a backend, a proxy
  not in force) to check a refusal; the refusal of a value given by variable, or typed at the
  plain prompt, keeps its test.
- **The plan's steps** came as one block: `writ` now sends them as items, numbered by the
  popup (asked by the user on the first build, `edacdc6`).
- **The rail's clicks** were taken by the hover popover; the card is now drawn over the window
  and never hit (`edacdc6`).
- **The quick start's repository step** first used the one-line `repo add`, which doesn't scan
  an unpinned host: the user pointed at the guided form, which does; the upstream key stayed a
  step of its own at their request (`760fdef`).
- **Secretive named as if required**: the operator pages name no approval agent any more, the
  popup's socket defaults to the installer's `SSH_AUTH_SOCK`, and the popup and `writ` say "your
  ssh-agent", never Touch ID (asked by the user, `a33f6db`).
- **A lease over several repositories** packed each per-repository term into one string in a
  narrow tile: found by the user testing the popup; a card per repository, chosen on mockups
  (`a7b9a59`).

## What was planned

[The roadmap's M7.9.5](../roadmap.md) as it stood:

Asked by the user after running the real install ([M7.9](m7.9-local-mode-checked-on-the-mac.md)):
what works is still hard to use. Three things, from their own use. The operator docs don't say
in what order to do things: a quick setup guide is missing (the keys, upstream and signing,
with how a key is proven and what each signature is; then a template; then a repo). The guided
commands are plain line prompts, with no colour and no arrow selection. And the popup is hard
to read: too much at once with no clear place to look, the expiry as a full date rather than
"in 2h", and an amendment that adds one path prints every path. The forks settled with the
user at its start: [decision log](../decisions.md), 2026-11-15.

- **Amendments show only what changed**, in `writ sign` and in the popup alike (`writ-cli`'s
  display, written once for both): a list field's change as the items removed and the items
  added (`- src/old.rs`, `+ src/new.rs`), never both whole lists; a scalar's as before and
  after. Times reach the app as structured fields beside their row, so it shows them relative
  ("in 2h") without reading anything out of a value. The trusted display's guarantees stay
  whole: every change shows, two different lists never read the same, an item's order or
  repetition that changes what is enforced shows too.
- **The popup redesigned, its design validated first.** Before any Swift is written, the
  window is designed as an artifact the user reviews (mockups from real
  tickets in light and dark: a new ticket, an amendment, a renewal, several waiting) and
  iterated on until they validate it. Then built to it, the panel's rules kept (above every
  space and full-screen app, no default button, no button that takes the focus, both held a
  second, the app styling by tag and never by content). **Validated (2026-11-15): three
  panes**, and a rail of the waiting tickets on the left only when more than one waits
  (badges by kind, a card with the title and repositories on hover; chosen by the user over
  tabs and a pager, to give the panes the width). In the centre what is signed: a header (the kind,
  the lease it touches, the title quoted as the agent's, the time left relative with the
  clock time beside it), every enforced term as a tile (none folded away), the expected
  paths as a file tree, who asks in one line, then the other leases and the details,
  folded. On the right the agent's words alone (task, plan, estimate, origin hint), marked
  untrusted, scrolling on its own so text of any length never moves the terms. The paths'
  tree: one path per row under its folder, a folder holding only one folder merged into one
  row, a count per folder (which folds), a pattern badged (`**` "everything inside"), a long
  name wrapped and never cut, the card scrolling past 320 px, a Tree / List switch and a
  filter; built by `writ` and sent as a structure, so the app never splits a value. An
  amendment opens on what changes (paths added and removed shown whole, the kept ones
  folded in the tree), its task before and after in the right pane; a renewal on now → if
  signed, the counts carried over, and the chain. Over several repositories (validated on
  mockups after the user's test): the lease's own terms in one strip, then a card per
  repository with its terms and paths; each change names its repository.
- **One prompt layer, on `inquire`** (`writ-cli`'s `prompt` module): a select with arrow keys
  and type-to-filter, a multi-select, text with inline validation and a help line, a confirm;
  colour, `NO_COLOR` honoured; every value shown cleaned first (a scanned host key, a name
  from the policy, a remote's answer: [security.md](../security.md)'s display rules). The plain
  line prompts are kept when stdin isn't a terminal, so scripts and variables work as today.
  On it: `writ admin … add`, `edit` and `rotate`, `writ init`'s questions, `writ sign`'s
  prompt, `writ unseal`'s. The end-to-end pipeline drives the widgets through a pty with real
  keystrokes.
- **The installer's questions in Rust**: each question `deploy/frame.sh` asks on a terminal
  is drawn by `writ prompt` (a select, text or a confirm, its answer on stdout) with the same
  widgets; the frame keeps every check and makes every change. Every choice still asked
  before anything changes, the summary and its go kept; without a terminal the variables
  answer, as today. (Planned as one `writ` command asking them all into an answers file;
  settled while building it: one question per call, so no new file to read strictly.)
- **A quick setup guide** (`docs/operators/quick-start.md`, local mode on the Mac, from a
  finished `make install`): the upstream key (made by the daemon, added on the remote, the
  remote's host key pinned), the signing key (made, then proven on the remote with `writ
  prove-key`; what a commit signature is, what an approval is and its `writ-approval`
  namespace, which key makes which), a template, a repo, a first agent under `writ run`.
  [The operators' README](../operators/README.md), [setup](../operators/setup.md) and
  [daily operations](../operators/sealing.md) reorganised around it (what each thing is first,
  then each task); the reference pages kept. Its commands run by the pipeline (rule 18).

## Security checklist

1. **Inputs:** none new from outside. `writ prompt`'s arguments come from the installer's own
   script; `SSH_AUTH_SOCK` is the installer's default answer, checked like a typed one; the
   paths' tree and the plan's steps are built from items already cleaned.
2. **Authority:** not touched: every signature is the approval key's over the bytes shown;
   every policy change is checked whole by the daemon.
3. **Fail closed:** Esc, the end of the input or a no change and sign nothing; a confirm
   signs only on `y` or `yes`; the installer stops on Esc with nothing done.
4. **Audit:** not touched.
5. **Revocation:** not touched.
6. **Secrets:** never asked through `inquire` (a plain `String`): passphrases, the recovery
   key and tokens stay with `writ_crypto::passphrase`.
7. **Display:** a set's change shows every item removed and added, whole; the tree gives back
   every path exactly; agent text only in the agent's pane, marked untrusted; every option,
   question and help cleaned before it is drawn; the app picks rows by `writ`'s labels and
   styles by tag, never reading a value.
8. **Dependencies:** `inquire` 0.9.4 (MIT) with `crossterm` 0.29, default features off;
   `cargo deny` passes; its row in the stack.
9. **Guarantees:** the trusted display's row names the new tests.
10. **Threat model:** not touched; the operator docs now advise an approval key that asks
    every time (the local-mode row: agents run as you).
