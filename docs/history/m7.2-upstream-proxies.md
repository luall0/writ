# M7.2 — Upstream proxies

A repo's upstream reached through a named proxy of the signed policy, for remotes that answer
only from some addresses or only inside some network (a Tor onion service): SOCKS5 or HTTP
CONNECT, an optional password from the keystore, the upstream's name resolved by the proxy
alone; `writ admin proxy`, host key scans through a proxy; real proxies in `make e2e`
([gateway](../architecture/gateway.md#through-a-proxy),
[the operator's page](../operators/setup.md#a-remote-behind-a-proxy),
[policy reference](../operators/policy-yaml.md#proxies-proxiesname)). An intermediary
milestone the user asked for. The forks settled with the user at its start, and those settled
while building, are in the [decision log](../decisions.md) (2026-11-12, M7.2).

**Status:** done (2026-11-12). `make ci` passes on macOS (944 tests); `make e2e` passes (36
scenarios, scenario 25's two among them).

## What was planned

Some remotes answer only from given addresses (an office network, a VPN exit, a bastion), or
only inside a network (a Tor onion service). A repo can name a **proxy** the daemon reaches its
upstream through: every sync, push, notes push and host key scan for it goes through the
proxy, and nothing else does. The forks were settled with the user at its start
([decision log](../decisions.md), 2026-11-12, M7.2).

- **In the signed policy** (settled with the user): a fifth section, `proxies.<name>`, and
  `repos.<name>.proxy` naming one. Changed like the rest of the policy, by a signed change from
  the approver's machine, applied live (the repos using a proxy whose entry changes get their
  mirrors reopened). `writ admin proxy list|show|add|edit|set|remove`, the generic entry
  commands; `writ admin repo set <repo> proxy=<name>` (`proxy!` takes it off). A proxy a repo
  names can't be removed.
  - `proxies.<name>.url`: `socks5://[user@]host:port` or `http://[user@]host:port`, read
    strictly (a plain host name or address, an explicit port, no path, query, fragment or
    password: a password is a credential).
  - `proxies.<name>.credential`: a key id, `use: upstream`, `kind: token` and `host` the
    proxy's host: the password, added with `writ admin token <id>` like an upstream token.
    Required with a user in the URL, refused without one. One key is a repo's credential or a
    proxy's, never both. Missing from the keystore: the repos behind the proxy are refused,
    naming the command that adds it, as an HTTPS token is.
  - `proxies.<name>.connect_timeout`: how long reaching upstream through the proxy may take
    (its handshake and the tunnel's opening), `30s` by default, 1s to 5m (an onion service
    can take a minute).
  - At most 64 proxies.
- **Protocols** (settled with the user): **SOCKS5** (RFC 1928; with the credential, RFC 1929's
  user and password) and **HTTP CONNECT** (with the credential, Basic `Proxy-Authorization`).
  Only tunnels: never plain HTTP forwarding, so TLS (HTTPS upstreams) or SSH (with its pinned
  host key) stays end to end, and the proxy sees ciphertext. **Tor** is a SOCKS5 proxy
  (`socks5://127.0.0.1:9050`, or the Tor container's name): an `ssh://git@<name>.onion/…`
  upstream with its onion host's key pinned, as the user's own `ProxyCommand nc -X 5 -x
  127.0.0.1:9050` does. A `ProxyCommand`-like program run by the daemon is not offered (a
  signed change would choose a program the daemon runs); it is a [backlog](../backlog/README.md)
  idea.
- **The host's name is never resolved by the daemon** behind a proxy: the proxy resolves it
  (SOCKS5's domain address type, CONNECT's `host:port`), so an onion name works and nothing
  leaks to the daemon's DNS. Only the proxy's own host is resolved by the daemon.
- **How each upstream gets there**: the daemon's one-operation SOCKS5 socket of M4.5
  (`writ_mirror::proxy`) is what dials, through a **dialer** (direct, or through the repo's
  proxy), still to the registry's host and port alone, still counting what upstream sends.
  - `https://`: git's `http.proxy` is that socket, as today.
  - `ssh://` behind a proxy: ssh's `ProxyCommand` is the daemon's own program, `writd
    upstream-tunnel <socket> <host> <port>` (by absolute path, like the relay), which asks the
    same one-operation socket for upstream and relays ssh's stream; the relay still wraps ssh
    and caps it. Without a proxy, ssh connects as today (`ProxyCommand=none`).
  - The host key scan (`writ admin host add|rescan --proxy <name>`; the guided `repo add` with
    `proxy=` given scans through it) opens its handshakes through the dialer. The scan's
    signed request names the proxy (`writ-scan/1` gains an optional `proxy`, absent when
    there is none: the bytes of a scan without one don't change). A rescan defaults to the
    proxy the host's repos share.
- **What the proxy answers is untrusted**: the SOCKS5 replies read field by field (version,
  status, an address of a known type and length), the HTTP response's head at most 8 KiB, its
  status `200` only (a `407` says the credential was refused); any other answer, or none
  within `connect_timeout`, refuses the operation with a reason naming the proxy, cut and
  cleaned like everything upstream says. A failure reaches the audit line and the agent's
  terminal (why the proxy refused), never the password.
- **The password** is a secret like the token: read into memory wiped on drop, never
  printed or logged, sent only to the proxy's host. Over SOCKS5 and plain HTTP it crosses the
  network to the proxy in clear (both protocols' design): a proxy on the daemon's host or a
  trusted network, or one that needs no password (restricted by address), is the advice; a
  TLS link to the proxy is a [backlog](../backlog/README.md) idea. Recorded in the
  [threat model](../threat-model.md).

## What was done

- **`writ-core`:** `config::proxies` (`ProxyUrl`, read strictly; `Proxy`; the bounds), the
  `proxies` section between the pins and the repos in the canonical layout, `repos.<name>.proxy`,
  the cross-checks (a credential exactly with a user, a token on the proxy's host, a key a
  repo's credential or a proxy's, never both; a declared proxy; `connect_timeout` 1 s to
  5 min; 64 proxies), `Section::Proxies` and its fields for `writ admin`, `ProxyName`;
  `writ-scan/1`'s optional `proxy` (absent: the same bytes as before).
- **`writ-mirror`:** `dial` (the `Dialer`: directly, or a `ProxyRoute` with its password;
  SOCKS5 and HTTP CONNECT clients reading every answer as untrusted, the password's buffers
  sized up front and wiped, a proxy's words cleaned and the password taken out); the
  operation's SOCKS5 socket dialing through it and keeping why a dial failed
  (`MirrorError::Proxy`); `tunnel` (`writd upstream-tunnel`, ssh's `ProxyCommand` behind a
  proxy); `MirrorError::NoProxyPassword`; a repo reopened when its proxy or the proxy's
  password changes; the scan's handshakes over a dialed stream; `Mirrors::dialer` for a scan
  naming a proxy.
- **`writd` and the gateway:** the policy's proxies handed to the mirrors at unseal and at each
  registry change; the scan through the proxy its signed document names (refused, and
  logged, when the policy in force declares no such proxy or lacks its password), its audit
  line naming the proxy; `writd upstream-tunnel`.
- **`writ`:** `writ admin proxy list|show|add|edit|set|remove`; the proxy in `repo list`
  and `repo show`; `host add <host> proxy=<name>` and `repo add … proxy=<name>` scanning
  through it; `host rescan --proxy`, by default through the proxy the host's repos share.
- **Tests:** `writ-core` (every bound on both sides, the layout read back, field edits, the
  property test with a proxy), `writ-mirror` unit tests (hostile SOCKS5 and HTTP answers, the
  8 KiB head on both sides, the password in no message, the `ProxyCommand` and what it
  refuses), the integration tests `upstream_proxy.rs` (a test proxy in front of the ssh and
  HTTPS test remotes) and `scan_and_check.rs`, end-to-end scenario 25 (microsocks and tinyproxy
  on a `behind` network the daemon isn't on).

## Security checklist

1. **Inputs:** new ones, each in the [inventory](../security.md#untrusted-inputs) with its
   bounds and hostile tests: a proxy's answers, a proxy's URL, `writd upstream-tunnel`'s
   arguments; the scan request's optional proxy; the SOCKS5 socket's row now names ssh's
   tunnel as a client.
2. **Authority:** a proxy is named only by a signed policy change; a scan through one only by
   the approver's signed `writ-scan/1` naming it. No new grant or read.
3. **Fail closed:** an undeclared proxy, a missing password, a refusal, a malformed answer or
   silence refuses the operation with its reason; never a fallback to a direct connection.
4. **Audit:** syncs and pushes keep their lines (a proxy's refusal is their reason); a scan's
   line names the proxy, allowed or denied.
5. **Revocation:** not touched (a proxy holds no decision).
6. **Secrets:** the password is a keystore token (sealed, added with `writ admin token`),
   wiped on drop, never in `Debug`, a command line, a file or a log; its request buffers sized
   up front; what a proxy prints back has it, and its Basic form, taken out. It reaches the
   proxy in clear for SOCKS5 and HTTP: a residual risk in the threat model.
7. **Display:** a proxy's words are cleaned and cut like upstream's before reaching an
   agent's terminal or `writ admin`; `writ admin proxy` output escaped like the other nouns'.
8. **Dependencies:** none added (base64ct, tokio, russh's `connect_stream` already in use);
   the e2e images add Debian's `microsocks` and `tinyproxy` on the pinned base image.
9. **Guarantees:** a new line in the [registry](../threat-model.md#what-writ-guarantees),
   behind a proxy, with its tests.
10. **Threat model:** boundary 7 says what a proxy is trusted with; two residual risks (the
    password in clear to the proxy, what the proxy sees and can refuse); the forks were the
    user's.
