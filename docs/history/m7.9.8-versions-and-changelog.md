# M7.9.8 — Versions and changelog

Asked by the user before M8: every crate was `0.0.0`, no binary said its version, and nothing
told an operator what changed between two installs or what an upgrade would ask of them.
Now Writ has one SemVer version for the workspace, a hand-written
[changelog](../../CHANGELOG.md) whose every release says what an upgrade asks, checked by
`make check`; the binaries say their version, every reply of the daemon names it, `writ`
says when it isn't its own, and `make install` says which version replaces which, with the
notes in between. The forks settled with the user are in the
[decision log](../decisions.md) (2026-11-15, M7.9.8, and the row on the envelope). This
milestone closes as **0.2.0**, the first release made under these rules.

**Status:** done (2026-11-16). `make ci` passes on macOS (1234 tests) at 0.2.0, and
`make e2e` passes (42 scenarios).

**Found while building it:**

- **The version travels in every reply's envelope, not in `info`** (step 3): `info` reaches
  only readers, so the agents' commands would never hear of a mismatch, and a reply that
  doesn't parse, which is what two versions cause, couldn't be read for a version inside it.
  Read first from the envelope, it names both sides on every listener. A `writ` before 0.2.0
  can't read the new envelope; 0.2.0's Upgrading says to install both together.
- **A `writd` before 0.2.0 has no `--version`**, and a `writ` before 0.1.0 says `0.0.0`: the
  installer reads the installed `writd`, then its `writ`, and takes `0.0.0` as no version.
- **The check needs no git history**: CI checks out one commit, so "the version moves only
  with its release" is checked as "the newest release is the workspace's version", which
  forbids both a version moved alone and a release added alone.
- **The changelog's own `# Changelog` was refused** by the first version of its check, found
  by the check's tests (step 2).
- **`approval_popup` passed by luck** (`36027eb`): it compared two displays a second apart
  with only the `(in …)` times taken out, and the "Other active leases" rows' `59m22s left`
  differed whenever another scenario held leases from the same source. It failed once in step
  3's `make e2e`; both relative times are taken out now.
- **A daemon of another version can't be built in the tests**: the hint and the unreadable
  reply's words are tested on replies naming any version (`writ-proto`, `writ-cli`), the real
  daemon and `writ` of one version in the integration and end-to-end tests.

## What was planned

[The roadmap's M7.9.8](../roadmap.md) as it stood:

Asked by the user before M8: every crate is `0.0.0`, no binary says its version, and nothing
tells an operator what changed between two installs or what an upgrade will ask of them. The
versions an upgrade depends on exist, each on its own (the state's, 13; the policy's format,
2; the signed messages', `writ-admin/2`, `writ-ca/1`), and `writd check-upgrade` reads them,
never a release. Settled with the user ([decision log](../decisions.md), 2026-11-15):

- **One SemVer for the workspace**, `[workspace.package] version`, every crate on it as
  today (they aren't published, and the three binaries ship and are installed together).
  Before v1, a minor version per milestone closed, a patch for fixes between two; 1.0.0 when
  M8.5 closes. From 1.0, a major version for an upgrade that owes a signed `writ migrate` or
  that a `writ` of the previous major can't talk to. The first release is **0.1.0**:
  everything through M7.9.7, one changelog entry pointing at the [history](../history/README.md).
- **`CHANGELOG.md` at the root, written by hand** for the operator, in the Keep a Changelog
  sections (Added, Changed, Removed, Fixed, Security), each entry linking to its history page
  or doc for the details, and an **Upgrading** block per release: the state version, the
  policy format, whether `writ migrate` is owed, whether a `writ` and a `writd` of the two
  versions can talk (the protocol's messages refuse unknown fields: two versions talk only
  when no message changed between them, and the block says so), and what to do in which
  order. A change people see (a command, a flag, a key, a behavior, a refusal, an upgrade
  step) adds its line under `Unreleased` in the same change, as rule 15 asks of the docs; a
  milestone's close turns `Unreleased` into its release, with its date, and sets the version.
  `make check` checks the file's shape (the sections, one release per version, newest first,
  dates), that the workspace's version has its release, and that the version changes only
  with a release added. AGENTS.md's milestone steps and its definition of done say so.
- **The version shown:** `writ --version`, `writd --version` and `writ-sign --version`
  print the binary's name and version, each with its end-to-end scenario and coverage row
  (rule 18). The daemon's version is in every reply's envelope, read before the rest
  (settled while building it: an `info` field would reach only readers, and a reply that
  doesn't parse couldn't be read for it; a row in the threat model's
  [looked at, and not risks](../threat-model.md#looked-at-and-not-risks): the code is open and
  every release's fixes are in the changelog). `writ` says when its
  version isn't the daemon's, a hint only (rule 1: the daemon decides); a reply that doesn't
  parse names both versions when the daemon's can still be read, else as today.
- **The installer:** `make install` over an install says `upgrading <from> → <to>` (the
  installed `writd --version`, or its `writ --version` for a `writd` before 0.2.0, which has
  none; `0.0.0` is no version) and shows the Upgrading blocks between the two, and those not
  released yet, before the go, beside `writd check-upgrade`'s report; going back to an older
  version says so and asks the same go. A fresh install names its version.
- Docs: the operator pages ([install](../operators/install.md): the upgrade's from and to and its
  notes; the clients' settings: `--version`), [conventions](../conventions.md) (the changelog's
  rules, when a version moves), [clients](../architecture/clients.md) (the hint), the
  [approval API](../architecture/approvals.md) (`info`'s field), AGENTS.md (the milestone steps,
  the definition of done), the threat model's row.

4. The installer's from and to, its notes, going back.

## Left open

- **A `writ` and a `writd` of different versions talk only when no message changed** between
  them: every message refuses unknown fields. The changelog says so per release; a protocol
  that tolerates an older peer would be its own decision.
- **The installer isn't in the end-to-end pipeline** (M8's, `install.md`'s commands): its
  versions are covered by the installer's integration test.

## Security checklist

1. **Inputs:** one new client-side input, the daemon's version in every reply: a string,
   `MAJOR.MINOR.PATCH`, 32 bytes at most, or the whole reply is unreadable; the rest read as
   strictly as before ([inventory](../security.md#untrusted-inputs), hostile tests). The
   installer reads the installed binaries' `--version` and uses it only if it is digits and
   dots. The changelog check reads only the repo's files.
2. **Authority:** nothing grants or refuses on a version: the hint is a hint (rule 1), the
   daemon decides as before.
3. **Fail closed:** a malformed version makes the reply unreadable; a new `writd` that names
   no version stops the install; `make check` fails on a changelog out of shape.
4. **Audit:** unchanged.
5. **Revocation:** unchanged.
6. **Secrets:** none in a version, the hint or the notes.
7. **Display:** the hint and the unreadable message are built from a checked version; the
   installer's notes are this tree's changelog, shown as text.
8. **Dependencies:** none added (`tomllib` is Python's own).
9. **Guarantees:** none changed.
10. **Threat model:** a row in "looked at, and not risks": every reply names the daemon's
    version to whoever the listener let in.
