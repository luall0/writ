# M4.5 — HTTPS upstream

Upstream over HTTPS with a token, chosen by the repo's `upstream` URL ([Q4](../decisions.md)),
for remotes that are reachable over HTTPS only. The way the daemon reaches an `ssh://`
upstream is unchanged; an `https://` one gets the same guarantees by other means
([gateway](../architecture/gateway.md#https-with-a-token)):

| | `ssh://` (M4) | `https://` (M4.5) |
|---|---|---|
| Who upstream is | the operator's pinned host key | a certificate from the system's CAs, or only from `mirrors.ca_certs`; no redirect |
| The credential | a key in the `Signer`, through a one-operation ssh-agent socket | a token from the keystore, through a one-operation credential socket to the daemon's own helper (`writd upstream-credential`) |
| What upstream sends | capped by the relay around ssh (`writd upstream-ssh`) | capped by a one-operation SOCKS5 proxy on a Unix socket, which also reaches only the registry's host |
| git's transport | `ssh` only | `https` only |

## What was done

- **`writ_mirror::upstream`**: `Upstream::parse` picks `ssh://` or `https://` (`http://`
  refused: the token would travel in clear); `HttpsUrl` read strictly (a plain host name or
  address, the user of `[A-Za-z0-9._~-]`, no password, query or fragment); the authority
  parsing shared with `SshUrl`.
- **`writ_mirror::credential`**: `UpstreamToken` (1 to 1,024 printable ASCII characters, no
  space or newline, wiped, `Debug` redacted); `CredentialSocket`, served for one operation in
  `<state>/mirror/sockets/`, answering only `protocol=https` and the registry's host and port
  (each named once), 4 answers and 8 connections at most, 4 KiB requests within 30 s;
  `credential::helper`, `writd upstream-credential <socket> <operation>`: git's helper,
  relaying git's request and the answer, nothing on `store` or `erase`, never the token on its
  stderr.
- **`writ_mirror::proxy`**: `UpstreamProxy`, SOCKS5 (`CONNECT`, no authentication) on a Unix
  socket for one operation, connecting only to the registry's host and port (by name, case
  aside, or the URL's address), 16 tunnels at most, the handshake within 30 s, upstream
  reached within 15 s; what upstream sends counted across every tunnel against
  `mirrors.max_fetch`, every tunnel ended past it. Dropped, it ends every tunnel (a `JoinSet`
  owned by the serving task) and removes its socket.
- **`writ_mirror::git`**: no transport for any git the daemon runs unless an upstream
  operation allows its own (`git::allow`, `ssh` or `https`); `HTTPS_HARDENING`
  (`http.sslVerify`, `http.followRedirects=false`, no extra header, cookie, empty
  authentication, prompt or other credential helper).
- **The mirrors**: a repo reaches upstream through an `Access` built for each operation
  (`ssh://`: the agent socket and ssh command; `https://`: the proxy, the credential socket,
  the settings, `http.sslCAInfo` when the operator gave CAs, an empty private `HOME` so no
  `.netrc` answers); a sync past the cap is `TooLarge` whichever counted it; a certificate
  that doesn't verify is `Certificate`; whatever upstream says has the token taken out
  before it reaches an error. git 2.47 is required when a repo is `https://` (older ones drop
  the proxy's socket path and would ask a proxy on `localhost:1080`).
- **`writd`**: `mirrors.ca_certs` (an authority file, 1 to 1,000 PEM certificates and nothing
  else: `writ_crypto::tls::check_ca_certs`; rewritten into the mirror's run directory); tokens
  from the development keystore (`<keys>/tokens/<id>`, written by the operator, read with
  `read_secret`, missing or malformed stopping the daemon), loaded only by `writd run` so the
  commands that print a key work before any token exists; one credential id is a key or a
  token, never both; the new command in `COMMANDS`.
- **Tests**: unit tests for each part; `crates/writ-integration` gains an HTTPS test remote
  (`https_remote`: `git http-backend` behind TLS with a self-signed certificate, the token
  checked, able to hang, flood, redirect or print the token back) beside the SSH one, on the
  same repositories, and the gateway harness can switch its repo to it
  (`GitGateway::start_https`); `tests/https_upstream.rs` (eight syncs) and two pushes in
  `tests/upstream_push.rs`.
- **End to end**: Forgejo behind a TLS front (`forgejo-https`, socat with a certificate made
  at build time), a repository `https` reached with a Forgejo token for repositories, pasted
  into the keystore by the operator setup as the operator guide says (a new step, checked
  both ways), the front's certificate as `mirrors.ca_certs`; scenario 13, `https_upstream`.
- **Docs**: [gateway](../architecture/gateway.md#upstream) (the upstream section split: SSH,
  HTTPS, pushing), the [operator guide](../operators/setup.md#https-upstreams-and-tokens),
  [security](../security.md#untrusted-inputs) (five new inputs),
  [threat model](../threat-model.md) (the asset, boundary 7, a new guarantee, two residual
  risks), [decisions](../decisions.md) (six rows, Q37), lease model, signer, stack, testing,
  end to end.

## Findings

- **git keeps a proxy's Unix socket path only from 2.47**: tried before writing the proxy,
  with git 2.54 (macOS) and Debian 13's 2.47.3 against github.com through a throwaway SOCKS
  server. The daemon checks 2.47 at startup when a repo is `https://`; the integration tests
  need 2.47.
- **git has no byte limit on an HTTPS fetch either**, and HTTPS runs inside git (libcurl),
  so there is no program to wrap as the relay wraps ssh; counting on the way in (the proxy)
  works whatever the protocol version. A wrapping remote helper would have missed protocol
  v0's pack, which a child of the helper fetches itself.
- **Over HTTPS a push reads its refs in its own request**: the test remote moves upstream
  before that request, as the SSH one does before its advertisement; moved after it, the
  remote refuses with "cannot lock ref" instead of "stale info" (refused either way).

- **The milestone landed in three code steps, not four**: the integration tests need
  `writd upstream-credential` (git runs it), which rule 18 ties to its end-to-end scenario,
  so the mirrors, `writd` and the pipeline went in one step (each step passes `make ci`).

## The security checklist, for M4.5

1. **Inputs**: five new ones, each in the [inventory](../security.md#untrusted-inputs) with
   its bounds and a hostile test: the token file (`a_token_is_one_word_of_printable_ascii_and_never_printed`,
   `https_repos_take_the_operator_s_token_and_ssh_repos_a_generated_key`), `mirrors.ca_certs`
   (`a_ca_bundle_holds_certificates_and_nothing_else`,
   `the_upstream_ca_certificates_are_an_authority_file_of_certificates_only`), the credential
   socket (`only_a_request_for_this_upstream_over_https_is_answered`,
   `a_request_longer_than_the_bound_is_refused`), the proxy (`it_tunnels_only_to_upstream`,
   `a_name_matches_case_aside_and_other_commands_are_refused`, `past_the_cap_every_tunnel_ends`),
   the `https://` URL (`https_urls_are_read_strictly`). What an HTTPS upstream sends is bounded
   as an SSH one's (`tests/https_upstream.rs`).
2. **Authority**: nothing new grants or reads; the repo registry and `writd.yaml` (where the
   operator names an `https://` upstream and its CAs) stay authority files. Whether a lease
   may fetch or push is decided as before, whatever the transport.
3. **Fail closed**: a missing or malformed token, an unreadable CA file, a git older than
   2.47, a credential id that is both a key and a token stop the daemon; a certificate that
   doesn't verify, a redirect, a refused token, a request for another host, too many bytes or
   no answer fail the sync or push, with the reason.
4. **Audit**: unchanged: syncs and upstream pushes are logged as before, with the token taken
   out of upstream's words.
5. **Revocation**: nothing new holds a decision; the sockets live for one operation.
6. **Secrets**: the token is read with `read_secret` into memory wiped on drop, never printed;
   it reaches only the daemon's own git, through pipes, for one operation; never a command
   line, an environment, a URL, the mirror's config, a log or an error (tested on disk, in the
   audit log and on the agent's side, in the integration tests and end to end). It leaves the
   daemon's memory for each operation (a residual risk, written down).
7. **What people see**: upstream's errors keep their bounds, with the token taken out.
8. **Dependencies**: none new in the shipped graph (`zeroize` was in the tree already); the
   integration tests use `hyper`, `hyper-util`, `http-body-util`, `rustls`, `tokio-rustls` and
   `rcgen`, all in the tree already. The TLS front image installs `socat` and `openssl` from
   the pinned Debian base's suite.
9. **Guarantees**: "agents never get remote credentials" gains the HTTPS tests; a new row,
   "an HTTPS upstream's token goes only to the registry's host, over TLS it verified, for one
   operation", with its tests.
10. **Threat model**: the upstream credentials asset and boundary 7 cover HTTPS; two residual
    risks: the token leaves the daemon's memory for each operation (its own git holds it), and
    an HTTPS upstream is authenticated by the system's CAs unless `mirrors.ca_certs` narrows
    them.
