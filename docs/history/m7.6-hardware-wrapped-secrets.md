# M7.6 — Hardware-wrapped secrets

Each secret the daemon holds but can't keep in a signer unwrapped by a hardware key only when
used, and the daemon able to start with no one: the common unwrap interface
([platform](../architecture/platform.md)), the `piv-p256` stanza, the Secure Enclave as its
first recipient, the offline recovery key, the keystore's recipients in the signed policy,
unsealing with no passphrase, the SSH CA behind the `Signer` and rotated live, auto-unseal
switched from the CLI, the installer asking all of it
([signer](../architecture/signer.md#startup-and-sealing),
[gateway](../architecture/gateway.md#https-with-a-token),
[approvals](../architecture/approvals.md#writ-admin-ca-rotate),
[sealing guide](../operators/sealing.md)). The forks settled with the user at its start and
while building it are in the [decision log](../decisions.md) (2026-11-13, M7.6).

**Status:** done (2026-11-13). `make ci` passes on macOS (1016 tests), the Secure Enclave
scenarios on this Mac's real Secure Enclave and against the fake helper; `make e2e` passes
(37 scenarios: 26 is new, the recovery key, the recipients, the CA's rotation and
auto-unseal's switch from the approver's machine; 16 runs `writd init --ca-backend`). Three
items need the real install under `_writd` and run with
[M7.7](../roadmap.md#m77--local-mode-checked-on-the-mac), as the user decided: the
[manual check](../guides/manual-checks.md#local-mode-on-the-mac-m7)'s step 3c.

**Found while building it:**

- age writes a random grease stanza into every file (`…-grease`): counting it as a recipient
  made the reconcile rewrap every file at every pass; it is skipped.
- With one retired CA, a second rotation would have cut the first CA's leases short: every
  retired CA is kept with its own deadline.
- The `piv-p256` vectors had to come from the other implementation: age-plugin-yubikey's own
  code, checked against the crates.io index, run with the user's leave, both ways.

## What was planned

[The roadmap's M7.6](../roadmap.md) as it stood at its start, and the backlog page's design
(kept below): every secret wrapped to a hardware key that alone unwraps it, and unwrapped only
when used; the keystore's data key the same way, so unsealing needs no passphrase; a recovery
recipient; auto-unseal, opt-in, only with everything in hardware; the boot tier in hardware as
an option. Settled with the user while building it: the recipients in the signed policy, a
passphrase keystore with a recovery key too, the SSH host key behind the `Signer` left to the
backlog (russh has no hook), auto-unseal in the signed policy and switched from the CLI, the
installer asking the new choices.

## What was done

1. **The unwrap interface** (`writ-platform`): `KeystoreUnwrap`, one way to unwrap an age
   file's file key; `unlock::open`, the one place a keystore file is opened, each way tried in
   turn; the passphrase and an X25519 identity as implementations; its contract suite and a
   fake device.
2. **Secrets per use:** the mirrors hold a `TokenRef` (an id, the digest of the file in force,
   a source), the token unwrapped for each operation and a proxy's password for each
   connection, wiped after; one that can't be unwrapped fails that operation alone.
3. **`piv-p256`** (`writ-crypto`): wrap to a P-256 point, unwrap from any ECDH, hostile
   stanzas refused before any device sees them.
4. **The Secure Enclave recipient:** `writ-se`'s key agreement (`create-agreement`,
   `public-agreement`, `agree`), its blob framed under its own header, its point proven by a
   probe ECDH; `PivUnwrap` over any `KeyAgreement` device; the contract on the real Secure
   Enclave.
5. **The keystore's recipients in the signed policy** (`recipients`, `writ admin recipient`):
   a hardware key made by the change that declares it, the recovery key beside it (on a
   passphrase keystore too); the reconcile that wraps every file to them, after each change
   and at each unseal; `identity.recovery.age` and the recovery challenge; `writ recovery new`
   and `writ recovery check`; `writ admin token` sealing to every recipient; `writd init` from
   the policy.
6. **Unseal with no passphrase:** `writ info` says what opens the keystore, `writ unseal` asks
   only what it needs; `writd recover` takes the recovery key (never the hardware alone) and
   sets a new passphrase when the policy it recovers leaves no hardware recipient.
7. **The SSH CA behind the `Signer`** (7a: `CaSigner`, its own signer, `writd init
   --ca-backend`, the installer's `CA_BACKEND`) **and rotated live** (7b: `writ-ca/1`, `writ
   admin ca show | rotate`, every retired CA trusted until its last lease ends).
8. **Auto-unseal:** `unseal: approver | auto` in the signed policy, `writ admin auto-unseal
   status | on | off` (what is missing, each with its fix), refused at the change and at start
   while anything is in software, the automatic start logged and notified; the installer's
   `UNSEAL`, `RECOVERY`, `AUTO_UNSEAL`.
9. **The guide and the checks:** the sealing guide's step-by-step auto-unseal section, the
   recovery guide's new cases, the manual check's step 3c for M7.7.

## Design

Settled with the user at M7.6's start ([decision log](../decisions.md), 2026-11-13).

- **Keystore format (M5):** one age file per secret. M7.6 changes which recipients a file is
  encrypted to, never the format, and never a file's plaintext.
- **Two ways a keystore unseals, never both:** `identity.age` is what unseals, and what it is
  wrapped to says how.
  - **Passphrase** (M5, the only way without hardware: detached mode today): `identity.age`
    wrapped with the passphrase (age scrypt); every secret, tokens included, encrypted to the
    keystore identity's recipient.
  - **Hardware:** `identity.age` wrapped to the keystore's hardware **recipients**; the keys
    (the CA, the agent signing keys and their blobs, the upstream keys, the authority MAC key)
    encrypted to the keystore identity as before; the **tokens** encrypted to the hardware
    recipients and the recovery recipient directly, never to the identity. No passphrase
    exists: moving to hardware removes the scrypt wrapping, and the recovery identity takes its
    place wherever a passphrase was asked off the hardware path.
  - **The recovery recipient** (at most one; required beside a hardware recipient, optional on
    a passphrase keystore: decided with the user while building step 5) wraps the identity in
    a file of its own, `identity.recovery.age`, so it opens every key; on a hardware keystore
    it opens the tokens directly too.
- **The recipients in the signed policy** (decided with the user while building step 5,
  instead of a `writ-keystore/1` of their own): a top-level `recipients` section, each entry a
  hardware key (`backend: se-cryptokit`, made by the change that declares it, like a key, its
  `age1se1…` printed) or the recovery recipient (`recipient: age1…`), managed as the policy's
  sixth noun, `writ admin recipient list | show | add | remove`, with the same diff, signature,
  stale-version refusal, MAC at rest and audit as the others. Applied live: the daemon
  re-encrypts `identity.age`, `identity.recovery.age` and every token file to the new set
  (each written new, then moved over the old one; the unseal finishes a half-done change).
  Refused: a hardware recipient without the recovery recipient (one lost device must not lose
  everything), a backend the daemon lacks, and removing the last hardware recipient (back to a
  passphrase is `writd recover`, which sets one). `writd init` makes the keystore as the
  policy declares it.
- **The interface:** `KeystoreUnlock` becomes `KeystoreUnwrap` in `writ-platform`: one
  implementation unwraps one file key from an age file's stanzas (or says it has no stanza
  there), with its contract suite and a fake ([platform interfaces](../architecture/platform.md)).
  Implementations: the passphrase (scrypt, `identity.age` only), an X25519 identity (the
  keystore's own, and the recovery identity), and the Secure Enclave in
  `writ-platform-macos`. `SecretFiles` (the one seam a secret is read through) holds a list of
  them. Later backends (YubiKey PIV, TPM, KMS Decrypt) are more implementations.
- **The Secure Enclave recipient:** a CryptoKit `SecureEnclave.P256.KeyAgreement` key, made
  and used through M7.5's `writ-se` helper: `writ-se/1` gains `create-agreement` and `agree
  <stored> <point>` (the ECDH shared secret, checked for its length; the point checked on the
  curve before it is sent). Its blob is framed like a signing key's, with its own kind, and
  kept in `recipients/` in the keys directory, beside its public half: it can't be sealed to
  the identity it unwraps, and is usable only by that Mac's Secure Enclave, under `_writd`.
  No prompt (no access-control flag needing a user).
- **The stanza: `piv-p256`**, as age-plugin-yubikey and age-plugin-se write it (an ephemeral
  P-256 point, compressed, and a 4-byte tag of the recipient; HKDF-SHA256 over the shared
  secret; ChaCha20-Poly1305 over the file key), implemented in Writ's own Rust
  (`writ-crypto`): no plugin binary is ever run. The recipient prints as age-plugin-se's
  `age1se1…`. Checked against the plugins' own test vectors. A YubiKey or TPM recipient later
  reuses the same code with its own ECDH.
- **The recovery identity:** `writ recovery new`, best run on an offline machine, prints an
  age X25519 secret key once (for paper; never written to disk) and its recipient; any
  `age-keygen` identity works too. The recipient is registered with `recipient add recovery`.
  With it the daemon writes a **recovery challenge** (`recovery-check.age`: a random value
  wrapped to the recovery recipient, and that value's SHA-256), read with a reader key;
  `writ recovery check` reads the secret key on stdin and proves it opens the challenge,
  sending nothing back. Recovered files open with stock `age -d -i`.
- **Per use, no cache:** a token is unwrapped when an operation needs it (an HTTPS push or
  fetch, a proxy's password), handed on, and wiped; a token that can't be unwrapped (its key
  removed, the device refusing) denies that operation with the reason, the daemon running.
  With a hardware keystore the identity itself is wiped once the unseal opened the keys: a key
  made later is sealed to the identity's recipient (public), so an idle daemon's memory holds
  no identity and no token (the software signing keys, outside auto-unseal, stay as M5 left
  them). The notification tokens stay opened at unseal (exempt: a notification grants
  nothing).
- **Unseal:** `writ info` says how the keystore unseals; `writ unseal` asks for the passphrase
  only for a passphrase keystore, and always for the approver's signature. `writd recover`
  takes the recovery identity (stdin), or the passphrase on a passphrase keystore, never the
  hardware alone.
- **The CA behind the `Signer`:** the CA's certificates are signed through a `Signer` adapter,
  so the CA key can live on any backend (P-256 on the Secure Enclave). `writd init
  --ca-backend`; `writ admin ca show` and `writ admin ca rotate [--backend]`, a signed
  `writ-ca/1` bound to the CA in force, live: new certificates come from the new CA, and the
  gateway keeps trusting the old CA's public key only until the last lease it certified ends
  (bounded by the longest TTL), then drops it, one `admin` line each way.
- **Auto-unseal:** `unseal: auto` in the signed policy (default `approver`; decided with the user while building it, switched by `writ admin auto-unseal status | on | off`). At start, the daemon
  checks the keystore unseals by hardware + recovery, the CA and every declared key on a
  hardware backend, and no token encrypted to anything else; anything else refuses the start
  naming each one. The start is logged (`unseal`, "automatic") and notified.
- **Ruled out: keys derived from a signature** (sign a fixed challenge, hash it into a key).
  It needs a key that signs the same bytes the same way every time: Ed25519 does, but the
  Secure Enclave's, the TPM's and most KMS P-256 ECDSA signatures are randomized, so the same
  input never gives the same key. Decrypting keys (ECDH, KMS Decrypt) are made for this.
- **Ruled out: age 1.3's `p256tag`** (the newer tagged recipient): our age crate lacks it and
  its spec is newer; `piv-p256` is what both hardware plugins already write. **Writ's own
  stanza:** new crypto to review for no gain.


## Threat model impact

- A compromised agent gets nothing, as today.
- Disk theft, backups and images of the daemon host get only ciphertext; a memory dump of an
  idle daemon gets no secret.
- **Root on a live host is not stopped:** it can ask the hardware to unwrap as the daemon
  does, and unlike a signing key (whose use yields one signature, only while on the host) one
  unwrap yields the secret itself, usable from anywhere until it expires or is revoked. The
  [threat model](../threat-model.md) says so; secrets as narrow and short-lived as their
  remote allows ([narrower upstream credentials](../backlog/README.md#narrower-upstream-credentials))
  limit what that leaves.
- The Secure Enclave key's blob is a plain file under `_writd`: a copy restored on the same
  Mac (a backup) unwraps again; removing the key means removing every copy.
- The recovery identity opens everything: it is kept offline, and checked without being
  typed on a networked machine if the operator follows the guide.
- With a cloud KMS: a trusted third party (the provider and the account holding the key), and
  a network call on each use, failing closed.

## Security checklist

1. **Inputs:** new ones in the [inventory](../security.md#untrusted-inputs), each with its
   bounds and hostile tests: the `piv-p256` stanza, the Secure Enclave helper's agreement
   answers, the recovery challenge (client-side), the recipients' files, `writ-ca/1` and the
   retired CAs' record; the policy's `recipients` and `unseal` read strictly.
2. **Authority:** recipients, the CA and auto-unseal change only by an approver's signed
   change (the policy's version binding and MAC, `writ-ca/1` bound to the CA in force);
   recovery needs the host and a secret, never the hardware alone.
3. **Fail closed:** a stanza that isn't well made, a device that refuses or lies, a hardware
   recipient without the recovery key, the last one removed, a stale rotation, auto-unseal
   with anything in software: each refused with its reason, nothing written; a token that
   can't be unwrapped fails that operation alone.
4. **Audit:** each change its admin line (done or denied), a recipient made and a rewrap that
   fails an admin note, the automatic unseal its own `unseal` line.
5. **Revocation:** the deny list holds for a retired CA's certificates as before.
6. **Secrets:** tokens out of memory between operations; a hardware keystore's identity wiped
   after unseal; the recovery key never written by Writ; every rewrap in wiped memory, files
   written whole then moved.
7. **Display:** recipients, fingerprints and what is missing shown escaped.
8. **Dependencies:** `age-core`, `bech32` and `p256`'s `ecdh` used directly (all in the tree
   already; [stack](../stack.md)).
9. **Guarantees:** four new rows in the [threat model](../threat-model.md) with their tests
   (per-use tokens, the keystore's recipients, the CA's rotation, auto-unseal).
10. **Threat model:** the identity row (closed on a hardware keystore), the auto-unseal row
    (the signed switch), the CA's lifetime; root on a live host still not stopped (above).
