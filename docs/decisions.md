# Decisions

Every design decision, with its date and why. New decisions get a row at the end of the log
in the same change that implements them; questions to settle go under
[Open questions](#open-questions). Ideas for later are in the [backlog](backlog/README.md).

## Decision log

| Date | ID | Decision | Why |
|---|---|---|---|
| 2026-10-31 | Q1 | Design against **sloppy** and **prompt-injected** agents. Malware on an agent host is bounded by the lease; the daemon host is trusted in v1. | The agent is the realistic risk. |
| 2026-10-31 | Q2 | **Coexist with Secretive.** Secretive keeps my personal keys; Writ owns only agent keys. | Bounds the worst case of any approval to the agent keys. |
| 2026-10-31 | Q3 | **Dedicated agent signing key, commits under my name**, with a **distinct committer email** (e.g. `user+agent@…`). | Verified and attributable to me, while agent commits stay filterable and the key revocable on its own. The key and email must be registered/verified on each forge account where Verified status matters. |
| 2026-10-31 | Q6 | **Deny + notify** for any out-of-lease request. | Fail closed. |
| 2026-10-31 | — | **Forge-agnostic.** No reliance on GitHub rulesets or any forge-specific protection. | I use GitHub, Gitea, Forgejo and others. |
| 2026-10-31 | — | **The daemon is the agents' git remote (gateway) and the only thing that pushes upstream.** | Repo, destination ref and pushed content become strong checks, forge-agnostic. |
| 2026-10-31 | — | **Sign at commit time, verify at push time** via a ledger of commits signed per lease. | Commit hashes never change; only lease-signed commits reach upstream. |
| 2026-10-31 | Q15 | **Two deployment modes, one protocol:** detached (Linux, Docker, agents anywhere) and local (native on the Mac). | One place of trust for all agents, with a local fallback. |
| 2026-10-31 | — | **Signer-agnostic keys.** `Signer` interface; v1 software keys; later YubiKey PIV, TPM, Secure Enclave; generic ssh-agent backend possible where its socket is out of the agents' reach. | Start simple, move to hardware without redesign. |
| 2026-10-31 | Q12 | **Personal use** for now. | Not tied to client work. |
| 2026-10-31 | Q17 | **Sealed start.** Software keys live in an encrypted keystore; v1 unseal = keystore passphrase + approver signature via `writ unseal`. Hardware recipients (age plugins for SE / YubiKey) later, plus a recovery recipient. | Keys encrypted at rest; a stolen volume is useless. |
| 2026-10-31 | Q8 | **Active leases persist** across restarts (SQLite) and are reloaded after unsealing. | Container restarts are routine; sealing already gates them. |
| 2026-10-31 | Q20 | **Signer-agnostic approvals:** an approval is an SSHSIG (namespace `writ-approval`) from any key in the daemon's `approvers` file. v1: `writ sign` on the Mac signing with a **dedicated Secretive key** (Touch ID). Later: own Mac SE app, iPhone app; a YubiKey FIDO2 key as backup approver. | Start with what I already use; replacing Secretive later is just adding a key. |
| 2026-10-31 | Q18 | **Upstream credentials: SSH keys on my own forge accounts**, one per purpose/forge, each labeled with a `+alias` of my email. | Simple to set up everywhere. Trade-off: forges can't scope personal SSH keys per repo, so these keys have account-wide access and the daemon's repo registry is the only per-repo boundary. The `+alias` is a label for auth keys; it only matters to forges for signing keys (committer email). |
| 2026-10-31 | — | **Borrowed from secrets-dispatcher:** process chain checks in local mode (executable path only, name/args advisory), JSON audit log with the process chain, and a reversible `writ try`. | Proven ideas, cheap to adopt. |
| 2026-10-31 | Q22 | **Push mode configured per repo** in the registry: `gateway` (default, full checks), `proxy` (daemon relays the SSH stream, checks repo and refs, no mirror), `direct_ssh` (lent agent socket, host checks only). `direct_ssh` requires a repo-scoped deploy key unless `allow_account_wide: true`, and is flagged in the approval prompt. | Lets each repo pick its trade-off. Over direct SSH the repo path is hidden from the agent socket, so only the forge can scope it. |
| 2026-10-31 | Q23 | **`proxy` mode checks the ledger too.** The daemon buffers the incoming pack, indexes it in a temporary quarantine (`git index-pack`), walks the new commits, and checks each one against the ledger before relaying anything upstream. | Gives `proxy` the same commit guarantee as `gateway`, without keeping a mirror. Costs some latency and temporary disk on large pushes; `max_push_size` bounds it. |
| 2026-10-31 | Q9 | **Rust core** for the daemon and CLI (Linux container + native Mac). Swift only for the later Secure Enclave signer/approver app. | One codebase for both modes; mature SSH crates. |
| 2026-10-31 | Q16 | **SSH + daemon-issued certificates** for everything between agents and the daemon: git, signing, lease commands. | One channel; git speaks SSH natively; certificate expiry = lease expiry. |
| 2026-10-31 | Q21 | Detached daemon reachable from **LAN + VPN only**. | Nothing exposed to the internet; agents still work away from home. |
| 2026-10-31 | Q4 | **Upstream over SSH and HTTPS tokens**, chosen per repo by the `upstream` URL. Tokens live in the sealed keystore. | Covers setups where only HTTPS works. Bonus: GitHub fine-grained tokens can be limited to selected repos. |
| 2026-10-31 | Q10 | **Ticket workflow via CLI + agent skill.** I start an agent for a specific feature or fix; the skill makes it think through the scope first and submit a **ticket** (task, plan, repos, branches, limits) with `writ request`. I sign it (it becomes the lease) or refuse it with feedback, and the agent revises. Amendments for scope changes; `writ close` with a summary at the end. Omega Code plugin is a future improvement. | Agents work end to end on an agreed scope, without prompting me for each commit. The ticket text is agent-written: shown to me, never trusted by the policy engine. |
| 2026-10-31 | Q14 | **Every ticket must fit a template.** Templates (admin-approved) set the maximum scope; tickets outside every template are rejected before reaching me. | The agent writes its own ticket; a hard cap that doesn't depend on my attention at approval time is the right defense. |
| 2026-10-31 | Q11 | **No tag signing in v1.** | Releases stay a human act; `refs/tags/*` protected in the registry. |
| 2026-10-31 | Q19 | Mirrors synced **on demand + periodically**; no webhooks. | Works on every forge and fits LAN + VPN only. |
| 2026-10-31 | Q24 | **Path check configurable per template:** `paths_check: off \| warn \| deny` (default `warn`). A ticket without `expected_paths` skips the check unless the template requires them. | Useful guardrail, but some tasks don't map well to paths; each template decides. |
| 2026-10-31 | Q25 | **Ticket link configurable per repo:** `ticket_link: trailer \| notes \| ledger_only`. `trailer` = `Writ:` line required and checked; `notes` = git note, message untouched; `ledger_only` = nothing on the forge. The daemon never strips a trailer: that would change the commit hash and break the signature. | Some repos' commit conventions don't allow extra trailers. The ledger keeps commit → ticket traceability in every mode. |
| 2026-10-31 | Q26 | **Narrowing at signing time**, already in v1 through `writ sign` (interactive or flags like `--ttl 2h`, `--drop-repo`). Secretive signs the narrowed ticket; the daemon checks it is a strict subset of what the agent submitted and returns the final lease to the agent. | Saves a refusal round-trip; can never widen. Needs no dedicated app: the CLI is already the trusted display. |
| 2026-10-31 | — | **Name: Writ.** CLI `writ`, daemon `writd`, shim `writ-sign`, commit trailer `Writ: wrt_…`, approval namespace `writ-approval`. Agent requests are still called tickets; a signed ticket is a writ. | A writ is a written order under seal authorizing action within stated limits: exactly a signed ticket. "Leash" was dropped because StrongDM already ships an AI-agent policy tool named Leash. |
| 2026-10-31 | Q7/Q13 | Approvals are always cryptographic signatures; a notification click alone is never an approval. Notifications through a `Notifier` (Telegram in v1, see below). | Keeps approvals strong whatever the channel. |
| 2026-10-31 | Q30 | **Platform-agnostic core, modes as configuration.** Everything OS-, hardware- or deployment-specific sits behind an interface (`Signer`, `Transport`, `CallerAttestor`, `SessionWatcher`, `KeystoreUnlock`, `Notifier`) with implementations picked at startup; the policy sees only `CallerFacts`, and missing facts deny. macOS-only code lives in `writ-platform-macos`. Local mode moves to M7, before detached (M8). | Mac features (process chain, Secure Enclave, launchd) plug in without touching the policy, the gateway or the clients, and a Linux local mode can come the same way. The daemon already runs natively on the Mac during development. |
| 2026-10-31 | Q31 | **Gateway push checks run in git's quarantine.** `git receive-pack` runs with the gateway's own pre-receive hook (`core.hooksPath`), which forwards the ref updates and a per-push token to the daemon over a private Unix socket; the daemon decides, git drops the quarantine on refusal. The daemon never reimplements receive-pack. | Gives `gateway` mode the design's quarantine for free, with git's own connectivity checks; the ledger check (M4) walks the new commits there. Found in [M0](roadmap.md#m0--protocol-spike-gono-go). |
| 2026-10-31 | Q32 | **Free Secure Enclave options first.** Before paying for the Apple Developer Program, local mode tries a Personal Team keychain access group (Plan A), then a CryptoKit key under a dedicated `_writd` user (Plan B), then a YubiKey or the software signer under that user (Plan D), in the M0 spike. Whatever the signer, the local daemon is isolated from my user. The backend is built in M7.5, the isolation in M7. | Agents run as my user in local mode, so a daemon running as me can't keep its keys from them. Every plan is a `Signer` backend, so switching is a config change. See [macOS Secure Enclave](architecture/macos-secure-enclave.md). |
| 2026-10-31 | Q33 | **Local-mode signer: a CryptoKit Secure Enclave key under a dedicated `_writd` user** (Plan B, backend `se-cryptokit`). The local daemon is a LaunchDaemon running as the role user `_writd`, its key blob and state in a `0700` directory. Settles Q27. | The M0 spike: Plan B passed every check (no prompt, screen locked, after reboot, nobody logged in; my user can't read, use or attach). Plan A worked but any code signed with my team could use the key; kept in the backlog for a paid account. |
| 2026-10-31 | — | **Canonical ticket encoding: compact JSON in a fixed field order**, `"kind":"writ-ticket/1"` first, sets sorted and deduplicated, sizes in bytes, UTC timestamps to the second. Decoding only accepts bytes that re-encode to themselves. Pinned by fixtures. | Readable and decodable (`writ sign` decodes and re-encodes before signing), deterministic with integers only, and the `kind` keeps a ticket approval from ever being read as another signed document (admin change, unseal). |
| 2026-10-31 | — | **Templates cap every part of a ticket:** they gain `force_push`, `committer_emails` and `signing_key` (required with `commit_sign`), and every limit is required. Omitted ticket limits take the template's maximum, omitted emails the template's. Push modes default to `[gateway]` for templates as for repos. | An agent writes its own ticket: an uncapped field (a personal committer email, another signer key, force push) would depend on my attention at signing time ([Q14](#decision-log)). |
| 2026-10-31 | — | **`expires_at` is fixed at submission** (`created_at + ttl`) and signed; waiting for my signature counts. Pending tickets expire too. | The signature covers an absolute end; an approval held back and replayed later can't start a fresh lease. |
| 2026-10-31 | — | **Amendments apply in place:** the lease keeps its id, certificate and counters and takes the amendment's terms; the amendment's record becomes `applied`. Revisions name the refused ticket (`revises`), which carries the feedback and the revision number. | `Writ:` trailers, certificates and the ledger keep pointing at one lease id for the whole task. |
| 2026-10-31 | — | **A lease that allows `fetch` is never exhausted**, only stopped per operation (signatures, pushes) and by expiry. | Found by the narrowing property test: with "exhausted when its counted operations are used up", narrowing away `push` revived a used-up `[fetch, push]` lease. Monotone now. |
| 2026-10-31 | — | **Signing names the repo, the ledger records it, a push needs a ledger entry for the same lease and repo.** | `ticket_link` and the path rules are per repo; a commit signed under the rules of one repo can't be pushed to another. |
| 2026-10-31 | — | **A lease is used only while it still fits its template under the current config**; deleting a branch counts as a force push; only `refs/heads/*` can be pushed. | Fail closed: tightening a template takes effect on active leases at once; a deletion loses commits like a force push. |
| 2026-10-31 | — | **Branch and ref patterns: an exact name or a prefix with one trailing `*`.** | Pattern coverage (template fit, narrowing) must be exact; full globs would make "within" undecidable in practice. |
| 2026-10-31 | Q29 | **The approval API speaks the gateway's SSH protocol on its own listener** (port 2223 in detached mode; HTTPS too, see the next rows), through the same `Transport` trait as the agents' listener. Clients pin the daemon's SSH host key in `~/.writ/known_hosts`; the approver's connection authenticates with a throwaway key and grants nothing, since only an SSHSIG grants. The M5 passphrase will travel in that SSH channel. Settles Q29. | One protocol and no TLS stack. Local mode gets a second socket with no change, and a separate listener can be firewalled to the approver's Mac. |
| 2026-10-31 | — | **Refusals and revocations: `decisions: signed \| open`** in `writd.yaml`, default `signed`. Signed means an SSHSIG (namespace `writ-approval`) over a `writ-refusal/1` or `writ-revocation/1` document (canonical bytes, `kind` first, `writ_core::signed`). With `open`, anyone who reaches the approval listener may refuse or revoke; a signature that is given is still checked. | The user's choice. Fail-closed by default, with the instant, unsigned revoke available when wanted. `open` adds a residual risk (denial of service only, [threat model](threat-model.md#residual-risks-v1)). |
| 2026-10-31 | — | **Two SSH users on the agents' listener:** `git` accepts only session certificates for an active lease (git, `writ-sign`); `writ` accepts a plain key that may only run `writ request` and `writ wait`. The key of a submission becomes the ticket's session key, so the submitter proves it holds it. Only that key can wait on the ticket. | OpenSSH falls back from a refused certificate to the plain key. A separate user keeps a revoked certificate from getting in as a submitter, and binding the session key to its holder needs no extra step. |
| 2026-10-31 | — | **A lease bound to a process (`subject.caller`) is granted only if the `SessionWatcher` can watch that process**; with the no-op watcher the approval is refused. When the process exits, the lease is revoked. | Such a lease must not outlive its session (fail closed). Over TCP it couldn't be used anyway. |
| 2026-10-31 | — | **Notifications are notifier-agnostic, Telegram in v1** (the Bot API's `sendMessage`, plain text, no `parse_mode`), replacing ntfy. The bot token is read from a `0600` file and moves into the sealed keystore in M5; it never appears in an error, `Debug` output or log line. Agent text is neutralized before it leaves the daemon. | The user's choice. Core code only sees the `Notifier` trait, so other sinks (native macOS, approver apps) plug in the same way. |
| 2026-10-31 | Q29 | **The approval API is also served over HTTPS** (port 8443), with the same commands, JSON bodies and replies (`writ_proto::Command::http_route`: `GET /v1/info`, `GET /v1/tickets[?all=true]`, `GET /v1/tickets/<id>`, `POST /v1/tickets/<id>/{approve,refuse,revoke}`). TLS 1.3 only, with a self-signed certificate the daemon generates (in the keystore). Clients pin its SHA-256 fingerprint in `~/.writ/tls_pins` (`writd tls-fingerprint` prints it), and no certificate authority is trusted. There's no client authentication, as over SSH. HTTPS connections come from a `Transport` and are attested like SSH ones. Agent commands stay SSH-only. | Approver apps (iPhone, Mac) speak HTTP more easily than SSH. Pinning keeps the same trust model as the SSH host key. |
| 2026-10-31 | — | **Each approval transport can be enabled or disabled** (`transports.approvals.ssh`, `transports.approvals.https`: an empty or omitted list disables one). With both disabled, `writd` refuses to start. Ports: `2222` agents (SSH), `2223` approvals (SSH), `8443` approvals (HTTPS). | Each deployment picks what its approvers use. Nothing could ever be approved without one (fail closed). HTTPS keeps 8443, as first planned. |
| 2026-10-31 | — | **Crates (M2):** `clap` for the CLI; `age` **0.11** (0.12 pulls `ml-kem` 0.2, whose `kem` pre-release can't coexist with russh 0.65's); `ureq` 3 for the notifier; `zeroize` for secrets; the russh client in `writ-cli`; `rustls` 0.23 (`ring` provider, like russh), `tokio-rustls`, `hyper` 1 and `hyper-util` for the HTTPS approval API on both sides, `rcgen` for its certificate. New crates `writ-platform`, `writ-proto` and `writ-approval`, as planned in the [layout](architecture/overview.md#repository-layout). | Settles Q28 for M2. `ring` everywhere: no second crypto backend (`aws-lc-rs` is kept out). |
| 2026-10-31 | — | **Random bytes never panic:** keys, certificate nonces, serials and ticket ids draw from bytes fetched fallibly from the OS (`writ_crypto::keys`), and a failure is an error. | Replaces M0's `UnwrapErr(SysRng)`, which could panic (AGENTS.md rule 11). |
| 2026-10-31 | — | **Audit before change (M2.5):** every grant, amendment, submission, refusal and revocation writes its audit line (synced) before the state changes; if the change then fails, a `denied` line with the reason follows. | Nothing is ever in force without its line; at worst the log holds an allowed line followed by its failure. Committing first and logging after left a window where an applied change had no line. |
| 2026-10-31 | — | **The gateway logs what it turns away on its own (M2.5):** callers the attestor can't attest (`connect`), commands it doesn't serve (`command`, new event), unknown repos, repos outside the lease, refused ref updates and signatures. | Hard rule 9: every deny writes one line, not only the service's lease decisions. |
| 2026-10-31 | — | **Revisions are not bound to a session (M2.5):** any session may revise a refused ticket; `writ request` makes a new session key for every ticket that isn't an amendment. | The feedback carried into the revision is the approver's own text to the agent, not a secret, and Writ has one user; amendments stay bound to the lease's session because they change a lease in force. |
| 2026-10-31 | — | **Fetch and push only on the lease's repos (M2.5):** the gateway refuses a repo that isn't in `scope.repos` before running git, in addition to the M0 protected-ref check (now per repo, from the registry). | The lease names its repos; M4 adds the full push checks on top. |
| 2026-10-31 | — | **Logs through `tracing` (M2.5):** library crates emit `tracing` events (lowercase message, structured fields) and never print; `writd` installs the subscriber (stderr, `WRIT_LOG`, `info` by default). `make check` refuses print macros in library code. | One way to log, filterable, and kept apart from the audit log, which records decisions and never goes through it. |
| 2026-10-31 | — | **Typed errors, named after their crate (M2.5):** `CryptoError`, `GatewayError`, `StoreError`, `PlatformError`, `ServiceError` (the approval service, converted to the wire `ApiError` only at the gateway, where internal causes are logged and never sent); causes kept as `#[source]`, not flattened into strings. | `writd` imports several crates' errors at once; a bare `Error` needs renaming at every use. Typed variants let tests match the error, not its text. |
| 2026-10-31 | — | **`Clock` is a platform interface (M2.5):** time comes from `writ_platform::Clock` (the system clock, or `FakeClock` in tests), with a contract suite like every other seam. | Every expiry, rate window and certificate validity depends on it; tests move it by hand instead of sleeping. |
| 2026-10-31 | — | **Hardened tests (M2.5):** tests are deterministic (they wait on signals, not on time; fakes for the clock; port 0; seeded property tests) and adversarial (exact denial codes, both sides of every limit, hostile input); AGENTS.md rule 12 and [testing.md](testing.md#hardened-tests). | Writ is a security boundary: a test that passes by luck hides a missing deny, and a flaky one gets ignored. |
| 2026-10-31 | — | **Three test levels (M2.5):** unit (one crate, on the fakes), integration (`crates/writ-integration`: the binaries and the real local tools, no external service, in `make test`), end to end (external services, Docker, `make e2e` from M4). | The crates working together are tested before any external service is involved, on every `make test`. |
| 2026-10-31 | — | **Property tests run twice (M2.5):** with a fixed seed (the same inputs every run, and every saved regression), then with a random seed printed for replay (`make test-props SEED=…`). | Reproducible runs, and still new inputs explored on every `make test`. |
| 2026-10-31 | — | **The TLS key behind the `Signer` (M5, M7.5):** the HTTPS approval API's key becomes one more `Signer` key, signed through by an adapter for rustls; the backend is a config choice (software `p256` by default from M5, Secure Enclave from M7.5). Changing backend changes the certificate, so approvers re-pin once. | It was the one key outside the `Signer`; behind it, it gets the same choices as every key (and, in hardware, never sits in the daemon's memory), with no change to the core. |
| 2026-10-31 | — | **Revisions are bound to the refused ticket's session (M2.5, replaces the row above that left them unbound):** a revision must come with the refused ticket's session key, like an amendment; `writ request` reuses that key (from `~/.writ/sessions/<refused>/key`) in the revision's own session directory. | Otherwise anything reaching the agents' listener could read the approver's feedback to another agent and pose as a follow-up of a ticket already reviewed. The cost: a revision is made on the host that submitted the refused ticket. |
| 2026-10-31 | — | **Reductions of privilege never wait for the audit log (M2.6, refines "audit before change"):** grants, allows, amendments, submissions and refusals still write their line first and are refused if the log can't take it. Revocations, withdrawals, expiries, exhaustion and ended sessions are applied either way: the certificate goes on the deny list first, the line is written first when possible, otherwise kept in memory (bounded) and written as soon as the log can take it, with a loud error meanwhile. | A full disk or a broken log must never keep a lease alive. Refusing a revocation for lack of a log line turned the audit log into a way to block one. |
| 2026-10-31 | — | **The lease is checked again when the ref updates are known (M2.6):** the pre-receive decision re-runs the lease check (state, deny list, expiry, caller, operation, repo); a revoked lease's pushes in progress are forgotten. | "Revocable instantly": a lease revoked while its pack was coming in moved refs after the revocation. |
| 2026-10-31 | — | **Session watches are rebuilt at startup, and an amendment keeps the whole subject (M2.6):** every active lease bound to a process is watched again when the daemon starts (one that can't be revokes its lease); an amendment can't add, drop or move `subject.caller`. In-memory state that enforces a lease is always rebuilt from the store. | Watches live in memory: after a restart, a lease outlived its session. |
| 2026-10-31 | — | **A transport's `accept` fails only when its listener is unusable (M2.6):** errors about one connection or a passing shortage (out of file descriptors, reset before accept) are retried inside with a backoff. | The daemon stops when a listener fails: one EMFILE from a peer opening connections ended it. |
| 2026-10-31 | — | **Only readers reach the approval API (M2.6, replaces "the approver's connection authenticates with a throwaway key" and "no client authentication" in the Q29 rows):** the daemon's `readers` file lists Ed25519 keys; the SSH approval listener accepts only those (no certificate), and HTTPS requires a client certificate for one of them (mutual TLS; the daemon compares its public key). `writ reader` makes the key on the approver's machine. Writes are still SSHSIGs on top. | Reads showed every ticket (task, plan, repos, leases) to anyone who reached the listener, and in local mode to every agent. The approval key can't authenticate connections (hard rule 8), hence a dedicated key. |
| 2026-10-31 | — | **Every agents' TCP listener names who may connect (M2.6):** `allow` (address ranges) is required on it, checked at accept before SSH starts; `0.0.0.0/0` must be written out. Optional on the approval listeners (readers only anyway). | Fail closed: anyone who reached port 2222 could submit tickets and phish an approval. |
| 2026-10-31 | — | **Bounds on what any peer can make the daemon hold (M2.6):** connections (256 per listener, 16 per source), 20 s to authenticate, 4 channels per connection, 30 s per request body; tickets (2 waiting per session key, 10 submissions a minute per address, at least 5 minutes each); a bounded notification queue that reports what it dropped; `writ ls --all` limited to the 200 most recent tickets. Denials before authentication are coalesced per source and minute, with a count. | Nothing an untrusted peer creates may grow without bound: memory, file descriptors, the approver's phone, the audit log's disk. |
| 2026-10-31 | — | **The session is checked before any state is revealed (M2.6):** an amendment or revision naming another session's lease or ticket gets "does not exist", whatever that lease's or ticket's state. | The answer differed by state, which told a stranger what became of someone else's lease. |
| 2026-10-31 | — | **Files that grant authority are checked like secrets (M2.6):** `writd.yaml`, the policy, `approvers` and `readers` are opened without following a link or blocking, and must be regular files owned by the daemon's user that group and others can't write (`writ_platform::fs::read_authority`); secrets must also be unreadable by others (`read_secret`). | Whoever could write `approvers` became an approver at the next start, bypassing signed admin changes; in local mode, that could be any agent. |
| 2026-10-31 | — | **The trusted display is bounded and ends on the enforced terms (M2.6):** 40 lines per agent field unless `--full`, blank runs collapsed, expected paths under the enforced scope, quoted lists, and a summary of what gets signed right before the prompt. The ticket itself: one-line title and plan steps, a task of at most 100 lines. `--yes` needs a named ticket. | A task and plan made of newlines (about 29,000 lines) pushed the scope out of the terminal's scrollback before `[y]es`. |
| 2026-10-31 | — | **Core hardening from the security review (M2.6):** protected refs match ignoring case (APFS); hidden characters come from a table generated from Unicode categories (Cc, Cf, Co, Cn, Cs, Zl, Zp and default-ignorables: `tool/gen-hidden-chars.py`), never a hand-written list; committer emails are printable ASCII; every YAML document is parsed with explicit options (no anchors, aliases or merge keys, one document, strict booleans, bounded size, depth and nodes) and `serde-saphyr` is built without `include` or `properties`; caller constraints are normalized, bounded and compared byte for byte; the feedback limit lives in core; upstream URLs can't hold a password or a user or host starting with `-`; who signed a refusal is recorded (schema 3) and unsigned feedback is labeled. | Each was a way around a check, or a check relying on a library default. |
| 2026-10-31 | — | **Algorithms and objects decided by policy, not defaults (M2.6):** the gateway's SSH algorithms are listed (no compression: `flate2` dropped; modern kex, AEAD ciphers, Ed25519 and P-256 keys); approver keys are Ed25519 or P-256 (or `sk-` forms) and session keys Ed25519 or P-256, checked at load and at submission; `sk-` approvals need the user-presence flag; a certificate with any critical option is refused; `receive-pack` checks every object (`fsckObjects`) and caps the pack; a poisoned session table refuses a new session and still drops revoked ones. | What a library or a build feature happens to accept is not a decision: each was something the daemon accepted without meaning to. |
